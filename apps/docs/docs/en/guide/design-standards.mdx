# Interface design and composition

For tools, management interfaces and data-dense pages, build hierarchy with neutral surfaces and a slight sense of physical depth: compact controls, clear container spacing and quiet headings keep content and data in front. Preserve an existing project's design system instead of turning every page into the same dashboard template.

This guide covers component composition and the scales for custom page layouts. Numbers describe defaults without theme overrides, not CSS values to hard-code again. Explicit component props, regional density and user theme overrides take precedence. See [Theming](/en/guide/theming) and [Theme tokens](/en/api/theme-tokens) for complete configuration.

## Read the visual language through components

| Component | Current appearance | Page composition |
| --- | --- | --- |
| [Menu](/en/components/menu) | Defaults to `raised`: a selected content surface, fine border and light shadow on a muted canvas. | Retain the selected surface instead of adding another indicator or a large brand-colored background. `default` and `primary` are other explicit appearances. |
| [Button](/en/components/button) | Defaults to `outline`: a neutral content surface and border with a slight resting shadow. | Keep ordinary actions neutral; reserve `solid` for important actions rather than emphasizing every button. |
| [Card](/en/components/card) | `variant="layered"` puts a small muted heading on the canvas and content on an inner surface. Card itself still defaults to `default`. | Use `layered` for independent tasks needing a heading/content separation. It does not display `description`; put important explanations in the body or a standalone CardTitle. |
| [DataTable](/en/components/table) | Defaults to `layered`: a quiet header and inner data surface share the layered Card relationship. | Place the main table and its toolbar directly, usually without another layered Card around them. Consider `simple` when embedding a table in an existing content surface. |

Canvas and content surface are roles, not fixed light gray and pure white. Preserve their grouping when users change surface colors or switch to dark appearance. Retain each component's selected surface, checkmark, border or indicator; do not impose either "selection never has a background" or another page-level brand highlight.

## Organize the page

- Establish the page heading, task sections and data regions before choosing containers. Let the page heading carry the main hierarchy; not every section needs a large bold heading. Keep actions near their content.
- Separate navigation, page header, toolbar and content responsibilities. Use Menu for navigation, Flex / Grid for peers, Card for an independent task, and DataTable directly for data.
- Use spacing to show relationships. Do not add cards, dividers and shadows to every paragraph or field. Separate page-level and row-level actions; prefer one primary action per task region.
- Compact controls do not require crowded content. Keep spacing consistent within groups and wider between sections. Wrap long labels instead of shrinking text and hit targets to fit.

## Type size and weight

| Text role | Default size / line height | Usage |
| --- | --- | --- |
| Body | 14px / 20px | `--leaf-font-size` / `--leaf-line-height`; regular body weight is 400. |
| Secondary, small text | 13px / 18px | `--leaf-font-size-sm` / `--leaf-line-height-sm`. `Text tone="muted"` changes color only, not size. |
| Large text | 16px / 22px | `--leaf-font-size-lg` / `--leaf-line-height-lg`. Do not enlarge every label. |
| Controls and ordinary section headings | Default weight 500 | `--leaf-font-weight`; use Button, CardTitle and other existing components, not an extra 600 override. |
| Strong text and prominent headings | Default weight 700 | `Text strong` or heading components; headings use `--leaf-heading-weight`. Do not make all body text bold. |

Prefer Typography, Text, Paragraph, CardTitle and Title. Custom page roots should inherit `--leaf-font-family`, `--leaf-font-size` and `--leaf-line-height`; ConfigProvider supplies variables but does not automatically apply library typography to arbitrary native text. The default family starts with Inter and includes system and Chinese fallbacks. Continue inheriting `theme.fontFamily` rather than adding a display font.

CardTitle defaults for `sm / md / lg` are 14/20, 16/22 and 18/24px, with heading weight for the large size. Title's `level={1..6}` determines both semantics and default size: 2.3, 1.85, 1.5, 1.25, 1.1 and 1 times the base font size, with line height 1.3. This is not a rounded integer-pixel scale. Choose a meaningful heading level rather than using a large heading as a regular label.

## Spacing and density

| Spacing variable | Comfortable default | Compact default | Typical use |
| --- | --- | --- | --- |
| `--leaf-spacing-xs` | 4px | 3px | Closely related content such as a heading and short description. |
| `--leaf-spacing-sm` | 8px | 6px | Adjacent actions and compact control groups. |
| `--leaf-spacing-md` | 16px | 12px | Groups within one content region. |
| `--leaf-spacing-lg` | 24px | 18px | Independent sections and page padding. |
| `--leaf-spacing-xl` | 32px | 24px | Larger section separation, not arbitrary padding on every item. |

Base spacing `--leaf-spacing` defaults to 8px in comfortable density and 6px in compact density. The rows above are 0.5, 1, 2, 3 and 4 times the base. Set regional density with `ConfigProvider density="compact"` or configure the base with `theme.spacing`; explicit theme and component settings take precedence. Compact density does not shrink body text.

Flex's `gap="sm|md|lg"` and Space's `size="sm|md|lg"` read these variables. Grid's `gap` does not resolve these names: use `gap="var(--leaf-spacing-md)"`. Pass CSS variables for xs / xl as well. Do not invent a slightly different pixel scale for each section.

## Dimensions, radii and shadows

| Geometry role | Comfortable default | Compact default | Usage |
| --- | --- | --- | --- |
| Control `sm / md / lg` height | 28 / 34 / 40px | 24 / 30 / 36px | Choose a local `size`; custom layouts read `--leaf-control-height-sm`, `--leaf-control-height` and `--leaf-control-height-lg`. |
| Form row / label gap | 16 / 6px | 12 / 4px | Let Form / FormField handle these; variables are `--leaf-density-form-gap` / `--leaf-density-label-gap`. |
| List row vertical padding | 12px | 8px | Let component density handle it; do not clip multiline content with a fixed row height. |
| Floating option minimum height | 30px | 26px | Follows control height; retain the component's keyboard and hit-target behavior. |
| Dialog block / inline padding | 20 / 24px | 16 / 20px | Retain the Modal / Drawer structure instead of inventing another dialog spacing scale. |

Size and density are separate dimensions. Use consistent `size` values in one row and ConfigProvider for regional density instead of scaling each control. Provide more generous touch targets rather than shrinking all actions to match a compact table.

Use `--leaf-radius-sm`, `--leaf-radius`, `--leaf-radius-md` and `--leaf-radius-lg`: defaults are 4 / 8 / 12 / 16px, derived from the base at 0.5 / 1 / 1.5 / 2 times. Components normally handle their own nested geometry; do not override internal `.leaf-*` radii.

Use the library's `--leaf-shadow-xs`, `--leaf-shadow-sm`, `--leaf-shadow-md` and `--leaf-shadow-lg` roles: outlined buttons and default Card have the lightest resting feedback, layered Card / Table use a light inner-surface shadow, and floating panels use higher levels. Prefer component defaults without adding duplicate shadows around containers. Hover does not lift, enlarge or raise shadow levels. Configure necessary overrides through the theme and preserve user `controlShadow` / `surfaceShadow` settings.

Input, InputNumber, InputSearch, Select, AutoComplete, Cascader, TreeSelect and single-value pickers default to 240px and do not resize after selection. Date ranges use 300px and datetime ranges 380px; allow more width for longer formats. Fields shrink in narrow containers and fill FormField; `style.width` overrides the default. Textarea remains full-width. Page layouts must not depend on these default widths remaining fixed.

## Use color roles, not fixed values

| Page purpose | Theme variables / component usage |
| --- | --- |
| Body and supporting text | `--leaf-color-text`, `--leaf-color-text-muted`; Text / Paragraph `tone`. Do not replace text roles with opacity on a whole paragraph. |
| Content surface, muted canvas, raised surface | `--leaf-color-surface`, `--leaf-color-surface-muted`, `--leaf-color-surface-raised`. A "white card" does not mean hard-coded white. |
| Frame, interactive border, divider | `--leaf-color-border`, `--leaf-color-border-hover`, `--leaf-color-divider`; do not use the frame color for every divider. |
| Brand-colored text on ordinary surfaces | `--leaf-color-primary-ink`, or `Text tone="primary"` / Link; do not use the raw brand color for small text. |
| Solid brand fill and its foreground | Pair `--leaf-color-primary` with `--leaf-color-on-primary`; prefer `Button variant="solid"` rather than manually specifying white text. |
| Success, warning, danger, information | Use the corresponding status component. Custom semantic text uses the family's `*-ink`, soft fills use `*-soft`, and solid fills pair with `on-*`. Status colors convey meaning, not section decoration. |

Change the brand color with `theme.primaryColor`; configure neutrals, surfaces and other semantic colors through `theme.tokens`, for example `neutralColor`, `surfaceColor`, `mutedSurfaceColor` and `dangerColor`. Page CSS reads the regional results. Do not copy defaults using fixed HEX values, numbered neutral shades or manual color mixing, or add a `:root` palette that overrides user configuration.

Preserve the existing theme, nested ConfigProvider and light/dark appearance. Overriding a base CSS color variable does not rerun JS derivation: update ConfigProvider configuration when related colors must change together. Default solid foregrounds do not guarantee readability for every custom fill; check actual text contrast after changing base colors and explicitly configure `onPrimaryColor` or other foregrounds when necessary.

Read the same variables in custom page classes rather than overriding component internals:

```css
.page-shell {
  min-width: 0;
  padding: var(--leaf-spacing-lg);
  background: var(--leaf-color-surface-muted);
  color: var(--leaf-color-text);
  font: 400 var(--leaf-font-size) / var(--leaf-line-height) var(--leaf-font-family);
}

.page-note {
  color: var(--leaf-color-text-muted);
  font-size: var(--leaf-font-size-sm);
  line-height: var(--leaf-line-height-sm);
}
```

Place the page within the current ConfigProvider region. These styles need not be redefined when users change the font size, base spacing or surface colors.

## Choose an appearance

- Use default outlined buttons for ordinary actions and `variant="solid"` for primary actions. Use `text` for quieter local actions, `link` for inline link-style actions, and `danger` for destructive actions.
- Do not add hover lifts, pressed scaling, colored halos or decorative gradients. Preserve component feedback instead of redesigning every state in page CSS.
- Input and picker fields use a primary-colored border on focus or while open, without an outer halo. Textarea, Mentions and InputNumber follow the same rule. Error, warning and disabled states retain their feedback; buttons retain a neutral keyboard focus outline.

## Themes and accessibility

Configure colors, light/dark appearance and local themes with ConfigProvider. Inspect [Colors](/en/guide/colors) and consult [Theme tokens](/en/api/theme-tokens) for individual settings.

On narrow screens, wrap control groups and turn columns into a single column in content order. Let tables scroll within their own region rather than overflowing the entire page. Do not clip descriptions, long labels or focus outlines with fixed heights.

Label form fields and icon-only buttons. Retain keyboard focus and error feedback; motion respects the system reduced-motion preference.

## Before delivery

- Use existing components and public tokens, without creating a second type, spacing, color or radius scale for the same purpose.
- Group by task and content, without meaningless nested cards, duplicate shadows or equally prominent headings everywhere.
- Preserve user theme and density overrides. Check hierarchy and actual text contrast in light/dark appearance and with custom brand/canvas colors.
- Wrap control groups on narrow screens, keep data scrolling local, and provide understandable loading, empty and failure feedback.
- Match the installed package's APIs. Query component documentation for behavior; this guide is not a complete API manual.
